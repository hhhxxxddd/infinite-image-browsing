# Spike：音视频内容检索的可行性与成本

状态：待验证；本文是实验计划，不代表音视频 AI 索引已经上线。

## 背景与目标

当前媒体扫描会将图片、视频、音频写入本地媒体库，可按文件名、标签和用户填写的描述检索。Qwen3-VL 向量索引只处理图片；视频没有逐帧或整段向量，音频没有转写或声音向量。现有视频封面只提取一帧供浏览；音频预览按需读取文件内或同目录的歌词、台词，它们尚未进入搜索索引。

本 spike 要回答：在不显著拖慢媒体库、不明显增加 Windows EXE 安装体积的前提下，能否让用户通过内容找到视频或带人声的音频？先做离线原型和小样本测量，再决定是否进入产品开发。复杂音视频编辑继续交给外部编辑器，不属于本计划。

## 待验证假设

| 方向 | 最小方案 | 要回答的问题 |
| --- | --- | --- |
| 视频画面 | 复用现有 Qwen3-VL-Embedding，对少量代表帧建向量；对比直接输入视频的向量 | 相比只索引封面，能否明显提高不同场景的召回？长视频需要多少帧或多少段？ |
| 音频台词 | 优先索引已有歌词、字幕；缺失时试用本地 ASR 转写，再以文字检索 | 中文、英文台词能否稳定找到？转写耗时及新增依赖是否可接受？ |
| 音乐与环境声 | 暂不选模型，只收集真实查询样例 | 用户是否确实需要按曲风、音色或环境声搜索？转写无法解决这些问题。 |

Qwen 官方的 Embedding 实现接受视频文件或帧序列，提供 `fps` 和 `max_frames` 参数；这只证明模型具备输入能力，**不等于本项目已经接通视频，也不能推定长视频的实际速度与效果**。现有检索封装只传入图片或文字，须在隔离实验中验证视频向量与现有文字查询的可比性。音频转写可用独立 ASR 原型评估，不应把“转写文本可搜索”称为声音语义检索。

## 实验顺序

1. **固定样本与基线。** 准备约 30 个短、中、长视频及约 20 段含中文、英文、无语音或带噪声的音频，覆盖当前媒体库支持的主流格式。为每类各写至少 10 条真实的内容查询，人工标记应命中的文件和片段。记录现有文件名、标签、描述搜索的结果；另在离线原型中建立“仅封面帧”和“仅已有歌词”对照组，因为当前界面尚不提供这两种内容搜索。实验只读取用户明确选择的本地样本；不提交原媒体到仓库。
2. **视频离线原型。** 在独立脚本或临时数据库中比较三种方式：现有封面帧、按时间稀疏抽帧并分别编码、模型原生视频输入。长视频分段处理，记录命中的时间段；限制每段帧数与分辨率，避免把整段视频解码到内存。测试无画面、损坏、旋转、可收录但无法解码等文件的降级行为。
3. **音频离线原型。** 先使用现有内嵌及同名歌词、字幕作为文字基线；只对缺少文本的语音样本运行本地 ASR。比较转写结果与人工台词，记录说话时间戳能否用于跳转。纯音乐及环境声单独统计，不将空转写视作“无内容”。
4. **对比检索与资源。** 对每种方案记录每小时原媒体的索引耗时、峰值内存与显存、向量或文本占用、单次查询延迟、失败率，以及人工标注查询的 Top-10 命中率。记录首次运行与增量更新，分别在目标 Windows 设备和 EXE 构建中验证。对照现有图片索引，检查后台索引是否影响浏览和播放。
5. **形成决策。** 逐项给出“采用轻量方案／继续研究／暂缓”，附样本、参数、结果、失败例和预计下载体积。若稀疏帧相对封面基线没有清晰收益，或音频转写不能覆盖目标查询，就暂不增加正式索引入口。

## 原型的边界

- 不改动当前图片向量表及搜索行为；实验结果单独存放，方便删除。正式实现才设计按媒体类型、模型版本、文件修改时间和抽样配置区分的索引结构。
- 不在普通媒体扫描时自动启动 AI 推理。若后续上线，应由用户选择媒体类型与范围，后台增量执行，可暂停、恢复和清理；文件移动、修改、删除及模型切换时要使对应条目失效。
- 不把模型权重打进 EXE。若音频方案需要新的 ASR 模型，单独列出下载大小、额外运行依赖、离线可用性与升级成本。默认本地处理；若将来评估云端方案，需另行设计用户可见的上传授权和费用提示。
- 不在这个 spike 中实现视频逐秒定位、声音相似度、自动打标签或音视频编辑界面。这些都需要独立的效果验证与产品设计。

## 决策门槛

视频进入开发前，应在预先标注的查询中，相比封面基线有明确的 Top-10 命中提升，且索引能在后台完成，不阻塞播放；长视频的时间与存储开销必须随分段上限可控。音频进入开发前，应证明转写确实改善台词检索，并明确纯音乐等无语音素材的处理方式。两者均需给出目标机器上的实测资源数据、失败恢复方案及 EXE 部署方案；没有这些数据时不承诺默认开启。
