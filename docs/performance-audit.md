# 性能排查记录（2026-09-23）

## 范围与样本

检查了目录图加载、增量扫描、媒体列表和翻页、文件夹范围过滤、缩略图、文字与 AI 检索。当前本机数据库有 498 条媒体、6 条已扫描目录；这是功能验证样本，无法代表十万张图片或网络盘的耗时。

## 已处理

| 路径 | 发现 | 调整 |
| --- | --- | --- |
| 子目录扫描 | 已记录目录的修改时间原先只精确到秒，短时间连续增删可能漏判；启动命令只扫描根目录时也可能跳过已变化的子目录。 | 目录修改时间改用纳秒；启动命令从过期目录列表扫描。页面的过期目录扫描本来会包含子目录，现也在“目录”页运行。旧时间记录升级后会触发一次补扫。 |
| 目录图 | 打开页面时递归读取多层节点，每个目录一次请求，宽目录可能造成大量并发请求与节点渲染。 | 初次仅读取根目录的直接子目录；更深的层级由节点按需展开。仅列目录时后端不再为每个子目录读取完整文件元数据。 |
| 媒体选择 | 全选后，对每张可见卡片用数组线性查找选中状态；拖动选中项时重复构造路径数组。 | 复用选中索引集合与拖动路径集合。 |
| 默认排序翻页 | 即使没有手动排序记录，也使用 `OFFSET` 跳过前面所有行。 | 没有手动排序时使用日期和 ID 游标；存在手动排序时保留原有位置顺序。 |
| 文件夹范围查询 | `substr(image.path, ...)` 条件无法利用现有路径索引。 | 改为字面路径范围条件，保留目录边界与“不含子文件夹”语义；Windows 增加忽略大小写的路径索引。实测 SQLite 查询计划从按日期扫描改为 `SEARCH image USING INDEX image_idx_path (path>? AND path<?)`。 |
| 卡片标签 | 每张卡片以数组展开和逐项查找生成标签状态，标签多时产生不必要的重复工作。 | 改为一次建立已选 ID 集合，再线性映射标签。 |
| AI 状态 | 开启画面搜索时每 2 秒请求模型状态；索引数量统计需要扫描媒体表。 | 改为每 10 秒轮询，且防止上次请求未结束就再次发出。 |

## 后续容量风险

| 优先级 | 路径 | 原因与建议 |
| --- | --- | --- |
| 高 | 语义搜索 | 每次查询遍历全部已索引图片，并对每张图片执行文件状态检查和向量点积。图片达到数万以上时应考虑向量索引或分批向量计算，并保留索引失效检查。当前没有大型图库基准，尚不宜直接替换排序算法。 |
| 中 | 目录变化检测 | 可见页面每分钟对所有已记录目录执行文件状态检查；本机 6 个目录负担很小，网络盘或数万目录时可能明显变慢。可考虑系统文件变更监听与低频完整核对。 |
| 中 | 已使用手动排序的深翻页 | 为保留自定义位置，仍使用 `OFFSET`，深页会反复跳过前面行。可考虑以位置和 ID 建立游标。 |
| 中 | 文字搜索 | 文件名函数、描述匹配及标签子查询在宽泛词下仍可能扫描大量媒体。更大图库可考虑专门的 FTS 索引，先用真实查询日志决定字段与分词方式。 |
| 中 | 极宽的单层目录 | 节点图仍会一次渲染一个目录的所有直接子目录。数千个同级目录时需要分批呈现或画布虚拟化。 |

缩略图已有视口附近加载、磁盘缓存和生成并发限制；媒体列表使用虚拟滚动。它们目前没有显示出同级别的结构性问题。

媒体索引的自动扫描与 Qwen 图片向量索引是两套流程：新增媒体会进入媒体索引，画面搜索所用的图片向量仍需在 AI 入口手动点击“更新索引”。

自动检查以目录修改时间为依据，新增、删除或移动目录项会触发所在目录的扫描；只修改已有文件的内容而不改变其所在目录时，目录可能不会被标记为过期。若需要可靠捕捉这种变更，后续应增加文件变更监听或定期核对文件级时间戳，不能把每分钟的目录检查视作完整文件校验。

## 工作台复查（2026-09-26）

此次为代码与回归检查，没有新增大型图库或高并发云端压测，不据此给出容量保证。

- 素材条先呈现 16 项，浏览时分批追加；“全部”网格按可视区域渲染，总览创建素材先显示 60 项。工作区素材元数据仍一次获取，素材条浏览到末尾后也不会移除已呈现节点，大工作区仍有线性增长成本。
- 悬浮大图延迟约 200ms 才加载，复用缩略图 URL；滚动与离开立即关闭，卸载时移除事件监听。结果元数据在打开预览时读取，不随任务轮询反复解析。
- 任务轮询在有排队／运行任务时为 2 秒，空闲为 15 秒；上次请求结束后再安排下一次，切换工作区和卸载会忽略旧响应。单个工作区最多返回最近 100 条任务，未完成任务优先。
- 后台任务并发为 1–15，未完成队列不超过并发数两倍（至少 4 个）。输入在内存中等待执行，因此高并发和大图仍会显著增加内存占用；该限额不是多进程共享队列。
- 切换工作区立即清除旧素材，避免新请求返回前把上一工作区产物呈现在当前编辑器中。

## 生成信息与预览审查（2026-09-27）

本轮对仓库运行全量前端类型／静态检查与现有前后端测试，人工审查重点为当前未提交的媒体预览、描述与 AI 建议、生成信息读写、资源添加和 ComfyUI 工作流相关调用链。不是逐行覆盖整个仓库，也没有新增真实大图库或远程模型压力测试。

### 修复与复用

| 问题 | 处理 |
| --- | --- |
| 参数展示与编辑采用不同的分隔规则，带逗号、引号或反斜杠的资源名称可能在保存后失真。 | 共用 `parameterEntries`，保留嵌套 JSON、转义路径和超出安全整数范围的 Seed；异常 Size／Hashes／AddNet 类型不再使解析器抛错。有效原始 JSON 不呈现为提示词，方括号开头的普通提示词仍可显示。 |
| 手动添加同名 LoRA 后，原始提示词中的旧权重优先，导致新值（尤其 0）看似没有保存。 | 补充资源的显式权重与哈希优先；资源合并使用 Map，避免逐项线性查找。 |
| 切换详情页签会重复拉取同一项元信息；慢响应可能污染新媒体的编辑状态。 | 当前项加载完成后复用，加载期间去重；保存／重试强制刷新。统一会话重置和请求失效处理，保存捕获原始路径及产物 ID，刷新保留正在编辑的描述和参考提示词草稿。 |
| 只显示参数标签仍会序列化所有补充信息；工作流标签提前生成完整 JSON。 | 紧凑面板跳过隐藏补充字段，工作流 JSON 延迟到复制时生成，遍历队列改用游标而非 `shift()`。 |
| 原文每次按键立即重解析；重复字段定义和样式累积。 | 复用 VueUse 180ms 防抖、共享参数定义和输入组件；移除预览内 66 条完全重复的 scoped CSS 规则，保留最终层叠顺序。纯文本解码函数从包含应用依赖的工具入口拆出，旧导入仍兼容。 |

### 可复现的局部基准

命令：`node vue/scripts/benchmark-generation-metadata.mjs`。本机 Node v24.20.0，合成 10,000 节点、2,346,706 字节的工作流对象；预热后测量 5 轮、每轮 20 次，报告每次耗时的中位数。

| 路径 | ms／次 |
| --- | ---: |
| 全部详情，包含补充信息序列化 | 5.690 |
| 紧凑详情，只读取显示字段 | 0.001 |
| 工作流检测并序列化复制内容 | 5.396 |
| 仅检测工作流与节点数 | 0.056 |

基准比较的是可执行的不同代码路径，不是整个旧／新版本的页面加载时间。输入是内存对象，不含网络、JSON 首次解码、Vue 响应式开销或 DOM 绘制；复制时仍需支付完整序列化成本。保留以上大图库风险，不能用此结果推导图库容量或端到端加速比例。
